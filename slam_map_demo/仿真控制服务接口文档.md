# MuJoCo 仿真控制服务接口文档

## 概述

本服务运行在装有 unitree_mujoco 仿真器的电脑上（当前为 `192.168.104.191`），让局域网内任何电脑通过 HTTP：

- 启动、重启、关闭仿真器（Go2 机器狗 + SLAM 地图场景）；
- 读取机器狗当前位姿；
- 让机器狗沿一条路线行走——路线可以是 A* 规划服务 `/plan` 的完整返回，也可以是一串坐标点；
- 不开窗口在纯 MuJoCo 中快速预演一条路线，得到是否能到达和俯视轨迹图。

仿真器和行走控制程序之间用 DDS 通信，只能在同一台电脑内进行，所以由本服务在本机代为执行。

| 项目 | 值 |
|---|---|
| 地址 | `http://192.168.104.191:8770` |
| 代码 | `slam_map_demo/scripts/sim_service.py`（行走控制复用 `follow_path.py`） |
| 运行方式 | 用户级 systemd 服务 `robot-sim-service`，开机自动启动 |
| 地图 | 启动参数指定，当前 `room1110/2026-11-11.2`，须与 A* 规划服务（端口 8765）一致 |
| 工作文件 | 服务器 `/tmp/sim_service/`：每次行走的路线、日志、结果，预演轨迹图，仿真器日志 |

坐标约定与 A* 规划服务相同：地图坐标系，米、弧度；原点为充电桩，x 轴为地图正前方，y 轴为 x 轴逆时针转 90°。
仿真世界的原点就是地图原点，A* 返回的坐标可以直接使用。

所有返回都是 JSON（轨迹图除外），以 `ok` 字段判断成败；失败时 `error` 为中文原因。
HTTP 状态码：200 成功；400 请求有误；404 接口不存在；409 当前状态不允许（如仿真器没运行、正在行走）；500 服务器端出错。

## 接口总览

| 方式 | 路径 | 作用 |
|---|---|---|
| GET | `/health` | 服务、地图、仿真器、行走状态、位姿、告警 |
| GET | `/pose` | 机器狗当前位姿 |
| POST | `/simulator/start` | 启动仿真器，同时拉起浏览器推流服务；`{"restart": true}` 重启（机器狗回到原点） |
| POST | `/simulator/stop` | 关闭仿真器和推流服务 |
| POST | `/walk` | 开始沿路线行走（立即返回，后台执行） |
| GET | `/walk` | 当前或最近一次行走的进度和结果 |
| POST | `/walk/stop` | 停止行走，机器狗站稳 |
| POST | `/control/start` | 默认创建持续轨迹会话，启动站立和步态控制 |
| POST | `/control/trajectory` | 更新局部或地图航点轨迹，由仿真内部 MPC 跟踪 |
| POST | `/control/command` | 按会话模式接收轨迹，或显式速度模式的 `vx`、`wz` |
| GET | `/control` | 最近一次持续控制状态、速度反馈和停止确认 |
| POST | `/control/stop` | 减速、站稳并释放该会话的控制权 |
| POST | `/preview` | 不开窗口预演路线（同步返回，约几秒到几十秒） |
| GET | `/files/<文件名>.png` | 下载预演轨迹图 |
| POST | `/controllers/stop_others` | 停掉不是本服务启动的遗留控制程序 |

POST 请求体为 JSON；没有参数的 POST 可以不带请求体。

## 持续轨迹控制

`POST /control/start` 请求 `{}` 等同于 `{"trajectory_timeout_s":2.0}`。
返回 `control_id` 后，查询 `GET /control` 等待 `state=running`、`ready=true`。
原 `/walk` 继续接收一次性的地图路线。新的持续模式允许在同一会话内滚动替换航点，
不重启控制器或重新站立；RPent／LightNav 调用方不需要计算速度。

`POST /control/trajectory` 请求如下，其中时间和位姿必须取自对应输入图像的观测，
不能直接照抄示例中的时间值：

```json
{
  "control_id": "control_实际编号",
  "seq": 1,
  "frame": "base_link",
  "stamp_ns": 1794638000000000000,
  "capture_pose": {"x": 0.0, "y": 0.0, "yaw": 0.0},
  "waypoints": [[0.1, 0.0, 0.0], [0.2, 0.02, 0.05], [0.3, 0.03, 0.05]]
}
```

| 字段 | 含义 |
| --- | --- |
| `control_id` | 本会话编号，每次更新复用 |
| `seq` | 本会话严格递增的非负整数，不要求与 LightNav WebSocket 序号相同 |
| `frame` | `base_link`：图像采集时机身坐标；`map`：地图坐标，须显式指定 |
| `stamp_ns` | 输入图像的主机 Unix 纳秒时间，来自 `/observation.stamp_ns` |
| `capture_pose` | `base_link` 模式必填，取 `/observation.base_pose`，至少含 `x,y,yaw`；map 模式不传 |
| `waypoints` | 1–64 行 `[x,y,yaw]`，米／弧度；局部每行均相对同一采集时原点，不累加 |
| `stop` | 可选布尔值；`true` 清空参考并站立，不代表语义任务成功，也不释放会话 |

LightNav 响应的 `data.actions.actions` 可以直接作为 `waypoints`，`stop` 也可原样传入。
局部点使用采集时位姿在服务内转换为地图参考；跟踪反馈使用当前 `base_link` 位姿，
而不是 `/pose` 的 IMU 原点。`waypoints:[]` 同样清空参考并站立，清空／停止参考不要求时间和位姿。

默认有效期 2 秒，可在创建会话时将 `trajectory_timeout_s` 设为 0.1–2.0 秒。
有效期从图像采集开始计算，不从 HTTP 接收时重置；新轨迹的采集时间也须递增。
过期、未来超过 50 ms、重复时间、旧序号返回 409，不刷新有效期；格式、有限数和坐标系错误返回 400。
同一图像不能通过递增 `seq` 重放续期。空参考／模型停止只归零并保留执行权。

服务内部使用项目内的 LightNav MPC 副本，按约 10 Hz 求解并跟踪参考，Go2 速度上限
0.3 m/s、角速度上限 0.3 rad/s。IPOPT 迭代限制 100，CPU 求解预算 0.1 秒。
MPC 采用与原实现相同的前向单轮模型，不直接执行横移；`y` 是路径位置目标。
解过期超过 0.5 秒、求解失败或轨迹超时会归零并收脚站立；旧轨迹的迟到解和迟到错误均被丢弃。
新有效轨迹可以恢复跟踪。MPC 的动力学和步态存在差异，仍需位置反馈，且本接口不进行地图避障。

`GET /control` 在轨迹模式下增加：

- `mode:trajectory`、`reference`：接受的序号、坐标系、采集信息及转换后的 `waypoints_map`；
- `tracking`：`reference_seq`、跟踪阶段、位置／朝向误差、求解耗时、求解结果年龄和错误；
- `trajectory_timeout_s`、`reference_age_s`、`watchdog_active`；
- `mpc_target`、`applied`、`motion`：服务内部 MPC 目标、步态设定及实际运动反馈，供诊断使用。

`tracking.reference_reached` 只验证当前短轨迹末端：位置误差不大于 0.15 米、朝向不大于
0.2 弧度，且已收脚、实测速度满足停止阈值。它不等于完整 VLN 指令已经完成。
调用方仍负责整体任务验收，并通过 `POST /control/stop {control_id}` 释放执行权。
新参考刚受理时返回 `reference_pending`，到达标记不会从旧参考继承。
`/control/command` 是该航点接口的别名，不接受 `vx/wz` 请求体。

## 停止确认与执行权

路线执行与持续轨迹控制使用同一个服务锁互斥。内部复用 Go2 步态、重力补偿及 DDS。
`POST /control/start` 只接受可选 `trajectory_timeout_s`，不提供模式选择或速度请求。
启动包含约 3 秒的站立过程；成功受理不表示已经站稳或完成运动。

结束时 `POST /control/stop`，请求体为 `{"control_id":"control_实际编号"}`。
服务等待减速、收脚及实测平面速度不大于 0.08 m/s、偏航角速度不大于 0.15 rad/s
持续 0.4 秒，再返回 `state=finished`、`stop_confirmed=true` 并关闭控制 writer。
客户端应留足约 9 秒停止等待时间。重复停止同一已完成会话可查询原结果，
旧编号不能停止或更新新会话。停止结果保存在运行目录 `work/control_*_result.json`。

`/walk` 与 `/control/start` 冲突返回 409，不自动抢占；`/walk/stop` 不停止持续轨迹控制。
持续控制期间不能重启仿真器，`/simulator/stop` 及正常服务退出会先清理自有控制。
DDS 过期、跌倒或执行异常时尝试发送阻尼指令，返回 `failed`、`requires_recovery=true`，
不会声称停止已确认；新运动被拒绝，需检查并重启仿真器恢复。
正常退出清理不能保证在强制杀进程时仍执行。

健康信息的 `control_mode` 仅包含 `idle`、`route`、`trajectory`、`blocked`。
`mpc_target`、`applied` 及实测 `motion` 是内部跟踪诊断，不是对外速度输入接口。
还未创建控制会话时 `GET /control` 返回 404。
可复现客户端和验证结果见 [本地部署说明](../../docs/LOCAL_DEPLOYMENT.md)。

## GET /health

```json
{
  "ok": true, "map_id": "room1110", "map_version": "2026-11-11.2",
  "scene": "scene_slam_room1110.xml", "scene_map": "room1110/2026-11-11.2",
  "simulator_running": true,
  "simulator_processes": [{"pid": 2581086, "cmdline": "./unitree_mujoco -r go2 -s scene_slam_room1110.xml"}],
  "pose": {"x": -0.051, "y": -0.007, "yaw": 0.0022, "tilt_deg": 6.0, "fallen": false},
  "walk": {"walk_id": "walk_091944_1", "state": "finished", "elapsed_s": 25.0, "exit_code": 0, "result": {...}},
  "other_controllers": [],
  "stream": {"enabled": true, "running": true, "url": "http://192.168.104.191:8771/", "processes": [{"pid": 2604709, "cmdline": "..."}]},
  "warnings": []
}
```

| 字段 | 含义 |
|---|---|
| `map_id`、`map_version` | 服务使用的地图包，须与 A* 服务 `/health` 的同名字段一致 |
| `scene_map` | 场景文件实际引用的地图版本，与上面不一致时 `warnings` 会提示 |
| `simulator_running` | 1 秒内收到过仿真器状态消息 |
| `pose` | 同 `GET /pose`，仿真器没运行时为 `null` |
| `walk` | 最近一次行走的简要状态，没有行走过时为 `null` |
| `other_controllers` | 不是本服务启动的控制程序（`waypoint_tour.py` / `nav_demo.py` / `follow_path.py`），会与本服务抢控制权 |
| `stream` | 浏览器推流服务：`running` 是否在应答，`url` 为观看地址（主机名取自调用方请求的 Host）；服务以 `--stream-port 0` 启动时为 `{"enabled": false}` |
| `warnings` | 场景版本不符、多个仿真器同时运行、有遗留控制程序等问题 |

## GET /pose

```json
{"ok": true, "x": 1.994, "y": -2.849, "yaw": -1.5347, "tilt_deg": 0.6, "fallen": false}
```

`tilt_deg` 为机身倾斜角，`fallen` 为 true（倾斜超过 30°）表示机器狗倒了，只能重启仿真器。
仿真器没运行时返回 409：`{"ok": false, "error": "仿真器没有运行，先 POST /simulator/start"}`。

## POST /simulator/start

| 请求体 | 行为 |
|---|---|
| `{}` | 没有仿真器时启动；已在运行时直接返回 `"仿真器已在运行"` |
| `{"restart": true}` | 关闭已有仿真器后重新启动，机器狗回到地图原点、朝 +x |

成功：

```json
{"ok": true, "message": "仿真器已启动，机器狗在地图原点", "pid": 2604089, "pose": {...},
 "stream": {"enabled": true, "running": true, "url": "http://192.168.104.191:8771/", "pid": 2604709, "message": "推流服务已启动"}}
```

耗时取决于场景大小：小场景约 5 秒，room1110 约 30 秒（服务最多等 90 秒），推流服务再加约 2 秒。

仿真器启动成功后（包括“仿真器已在运行”的情况），服务会确保浏览器推流服务 `scripts/sim_stream.py`（端口 8771）在运行：
没在运行就启动；加载的场景与本服务地图不一致就重启。局域网内浏览器打开 `stream.url` 即可观看，
或在网页中用 `<img src="http://<服务器IP>:8771/stream">`。推流失败时 `stream.running` 为 false、`stream.error` 说明原因，
不影响仿真器和行走；日志在服务器 `/tmp/sim_service/stream.log`。推流服务说明见 README 的“浏览器查看仿真画面”一节。
仿真器窗口显示在服务器桌面上；服务器没有登录桌面、或显存不足时启动失败（500，`error` 中带仿真器日志末尾）。
正在行走时返回 409。

## POST /simulator/stop

关闭所有仿真器进程（正在行走时先停止行走），同时停止推流服务。`{"ok": true, "message": "已关闭 1 个仿真器进程、1 个推流进程"}`

## POST /walk

请求体三选一：

```json
{"plan": { ...A* 服务 /plan 的完整返回... }}
{ ...A* 服务 /plan 的完整返回，直接作为请求体... }
{"points": [[0, 0], [2, 1], [2, 4]], "final_yaw": 1.57}
```

| 字段 | 必填 | 含义 |
|---|---|---|
| `plan` | 三选一 | A* 返回：按 `legs` 逐段行走，每段终点转到 `goal.stand_pose.yaw`（为 `null` 时不转身）；会核对地图版本 |
| `legs` 等 | 三选一 | 直接把 A* 返回整个作为请求体，效果同上 |
| `points` | 三选一 | 拐点列表（地图坐标系），整条算一段。点可写成 `[x, y]`、`[x, y, ...]` 或 `{"x": .., "y": ..}`，多出的列和键忽略，可直接接收 VLN 等其他导航算法的轨迹；点疏点密均可 |
| `final_yaw` | 否 | 配合 `points`：到达后的朝向（弧度）；不给则保持最后一小段的行进方向 |
| `force` | 否 | `true` 时路线穿过障碍也照走（默认拒绝） |

起点处理：机器狗离路线第一个点不超过 0.3 m 时从当前位置直接开始；更远时先走到第一个点（直线有障碍则用 A* 绕行）。
所以 A* 的起点应当用 `GET /pose` 读到的当前位置。

成功（立即返回，行走在后台进行）：

```json
{"ok": true, "walk_id": "walk_091944_1", "start_pose": {...}, "message": "已开始行走，用 GET /walk 查看进度"}
```

失败：

| 状态码 | `error` | 处理 |
|---|---|---|
| 409 | 仿真器没有运行 | `POST /simulator/start` |
| 409 | 机器狗倒了 | `POST /simulator/start {"restart": true}` |
| 409 | 上一次行走还没结束 | 等它结束，或 `POST /walk/stop` |
| 409 | 有其他控制程序在运行：… | 确认可以停掉后 `POST /controllers/stop_others`，最好再重启仿真器 |
| 400 | 行走程序拒绝执行：… 穿过障碍、未扫描区域或地图外 | 手写坐标改用 A* 规划；算法给出的轨迹让原算法重新规划，或确认无误后加 `force` |
| 400 | 行走程序拒绝执行：… 个点格式错误 | 点应为 `[x, y]`、`[x, y, ...]` 或 `{"x": .., "y": ..}` |
| 400 | 行走程序拒绝执行：规划结果来自地图 …，与本地地图包 … 不一致 | A* 服务和仿真服务的地图不一致 |

## GET /walk

```json
{
  "ok": true, "walk_id": "walk_153737_1", "state": "finished", "elapsed_s": 77.0, "exit_code": 0,
  "result": {"ok": true, "legs": [{"id": "wp_02", "name": "厕所通道", "reached": true,
                                   "position_error": 0.048, "yaw_error": 0.1, "time": 35.4},
                                  {"id": "wp_04", "name": "母婴室", "reached": true,
                                   "position_error": 0.047, "yaw_error": 0.1, "time": 35.6}]},
  "log": ["第 1 段 厕所通道：…", "[出发] 前往 wp_02 厕所通道：6.0 m，2 段折线",
          "[到达] wp_02 厕所通道：位置误差 0.048 m，朝向误差 5.7°，用时 35.4 s", "…",
          "[到达] wp_04 母婴室：位置误差 0.047 m，朝向误差 5.7°，用时 35.6 s", "[全程结束] …"],
  "last_status": "…",
  "fell": false,
  "pose": {"x": 0.711, "y": -4.492, "yaw": -3.1385, "tilt_deg": 0.5, "fallen": false}
}
```

| 字段 | 含义 |
|---|---|
| `state` | `running` 行走中；`finished` 已结束（到达、放弃、被停止或摔倒） |
| `result` | 结果，走完前为 `null`；`result.ok` 为 true 表示每段都到达。`result` 出现后程序还会站稳约 3 秒才变为 `finished` |
| `result.legs[i]` | `reached` 是否到达；`position_error` 位置误差（米，没到达时为放弃时离目标的距离）；`yaw_error` 朝向误差（弧度）；`time` 用时（秒） |
| `result.note` | 被停止或摔倒时出现 |
| `exit_code` | 0 全部到达；1 其他情况 |
| `log` | 关键日志（最后 30 行）：`[出发]`、`[到达]`、`[跳过] … 20 秒没有进展`（卡住，放弃该段）、`[摔倒]` |
| `last_status` | 最近一行状态：时间、阶段（`follow` 行走 / `align` 原地转向 / `pause` 停顿）、位置、朝向 |
| `fell` | 是否摔倒 |

行走速度约 0.18 m/s，另加每段约 5–10 秒的起步、转向和停顿；建议每 5–10 秒查询一次。

## POST /walk/stop

停止行走，机器狗站稳约 3 秒后控制程序退出，之后仿真器保持站立指令。返回中带 `walk`（同 `GET /walk`）。

## POST /preview

请求体与 `POST /walk` 相同，另可加 `"spawn": [x, y, yaw]` 指定出生位姿；不给时用仿真器中机器狗的当前位姿，
仿真器没运行则用原点。不需要仿真器，也不影响正在进行的行走。同步返回，耗时约为实际行走时间的十分之一：

```json
{"ok": true, "spawn": [0.0, 0.0, 0.0],
 "result": {"ok": true, "legs": [...]},
 "log": ["…", "巡航结束：用时 36 s，到达 1/1 个点位，行走中最大倾斜 4.1°，最深穿透 0.011 m"],
 "image": "/files/preview_091744_302_368.png"}
```

`image` 为俯视轨迹图（深灰为障碍、红线为轨迹、绿点为各段终点），用 `GET http://192.168.104.191:8770/files/…png` 下载。
预演没有全部到达时 `ok` 为 false，并有 `error`。

## POST /controllers/stop_others

停掉 `other_controllers` 中列出的进程，返回 `{"ok": true, "stopped": [...]}`。
这些程序被强制结束时机器狗可能停在半步姿态，之后建议 `POST /simulator/start {"restart": true}`。

## 服务器端维护

```bash
systemctl --user status robot-sim-service          # 状态
systemctl --user restart robot-sim-service         # 重启服务（不会关闭仿真器）
journalctl --user -u robot-sim-service -f          # 请求日志
```

换地图：修改 `slam_map_demo/systemd/robot-sim-service.service` 中 `ExecStart` 的地图包路径，
执行 `systemctl --user daemon-reload && systemctl --user restart robot-sim-service`；
A* 服务也要换成同一张地图（`nav_astar_docker/docker-compose.yml` 的 `NAV_MAP`）。
地图对应的场景文件由 `map_to_mujoco.py` 生成，见 `README.md`。

## 已知问题

- 机器狗实际停下的位置与目标有几厘米偏差，所以每次规划前都要重新 `GET /pose`；
- 站在地毯台面上时仍可能缓慢滑动：C++ 仿真器自带的 MuJoCo 3.3.6 在高度场栅格边缘会产生倾斜接触。平地已改由平面承担落脚，不再滑动（2026-11-10 修复）；
- 步态是手写的开环小跑，不能横向平移；急转弯时先停下原地转；
- 仿真中没有动态障碍。
